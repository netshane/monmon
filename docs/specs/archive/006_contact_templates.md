Allow the format of notification contact messages to be specified in a template in configuration.
Use jinja2 to expand the templates.

Use the following format `[contact.message.[type].[channel]]`.  Below are some examples:
```
[contact.message.alert.email]
batch_subject = ""
subject = ""
body = """
"""

[contact.message.report.email]
batch_subject = ""
subject = ""
body = """
"""
html = """
"""

[contact.message.info.slack]
subject = ""
message = """
"""

[contact.message.error.teams]
subject = ""
message = """
"""
```

There should also be templates for notify.
test-notify should use the template for the specified contact type and channel and provide placeholder values for the template variables.

A default template for each contact type should be set in `settings.toml` and can be overridden in the monitor configuration.
Create simple default templates for each contact type and channel in code to use if no template is specified in configuration.  This should include a default template for the batch_subject.

For combined notifications, the batch template should merge the results of each  template into a single message.
To handle this, render each monitor's fragment eagerly in notify() and hold the rendered string in _Pending.

The `batch_subject` configuration should be used for the subject of the combined notification.  If it is not set, the subject of the first monitor's template should be used.  `batch_subject` should only be defined in `settings.toml` and not in the monitor configuration.

When rendering templates, do not auto-escape plain text email bodies.  Other bodies should auto-escape rendered variables to prevent html injection and misrendering of messages.

All templates should be verified / compiled at monitor load time and any errors should be reported as a monitor load failure.

When merging child monitor settings any undefined settings from the parent should be kept.  For example, if the child monitor specifies a `body` template but not a `subject` template, the parent's `subject` template should be used.

If a monitor template fails to render, the monitor should log the error and continue to send notifications to other monitors.  The monitor should not fail to run if a template fails to render.
Length caps should be automatically applied to the rendered templates.  If a template exceeds the length cap, it should be truncated and an ellipsis added to the end of the message.

Batch fragments should be rendered eagerly at notify() time.  There should be one per alert.

Provide the following variables to use in the templates:
- `name` - the name of the monitor
- `description` - the description of the monitor
- `link` - the link setting for the monitor
- `tags` - the tags setting for the monitor
- `alert` - the alert object
- `reports` - the reports generated by the test
- `test_results` - the results of all tests
- `started_at` - the start time of the test
- `duration_seconds` - the duration of the test in seconds
- `status` - the status of the test
- `contact` - the contact object for the notification
- `contact_type` - the contact type for the notification
- `contact_channel` - the contact channel for the notification

The `batch_subject` configuration should provide the following variables to use:
- `monitor_count` - the number of monitors in the batch
- `monitor_names` - a list of monitor names
- `alert_count` - the number of monitors in the batch that generated alerts
- `report_count` - the number of monitors in the batch that generated reports
- `contact` - the contact object for the notification
- `contact_type` - the contact type for the notification
- `contact_channel` - the contact channel for the notification

For undefined variables, use a lenient strategy that does not raise an exception.  Instead, the undefined variable should be replaced with an "(Undefined)" string.

### New module - `locallib/message_templates.py`

- `MessageTemplateFactory` resolves and compiles templates.  Resolution is
  **field by field**: monitor `[contact.message]` -> `settings.toml`
  `[default.contact.message]` -> built in defaults.  A monitor that overrides
  only `body` keeps the `subject` it inherited (parent monitor templates are
  merged first by the loader's existing deep merge).
- `MessageTemplateSet` holds the compiled templates for one monitor and exposes
  `render(contact_type, channel, context)` and
  `render_batch_subject(contact_type, channel, context)`.
- Section keys are `subject`, `body` (alias `message`), `html` (email only),
  and `batch_subject`.  An empty string means "inherit" rather than "blank".
  Unknown types, channels, and keys are rejected, as is `batch_subject` in a
  monitor and `html` on a chat channel.
- Escaping: the plain text **email body is not autoescaped**; `html` bodies and
  chat `message` bodies are.  Subjects are plain text and are not escaped.
- Undefined variables render as `(Undefined)` via `LenientUndefined`
  (a `ChainableUndefined` subclass, so `{{ alert.value }}` is safe when `alert`
  itself was never provided).
- Length caps are applied to every rendered field, truncating with `...`.
  Defaults: subject 200, email 100000, slack 3900, teams 20000; overridable via
  `[default.contact.limits]`.
- Filters available to templates: `table`, `html_table`, `datetime`.

### Wiring

- `MonitorLoader` takes a `MessageTemplateFactory` and compiles each monitor's
  templates in `_build_definition`, so a bad template is a **monitor load
  failure** surfaced by `validate`.  The compiled set is stored on
  `MonitorDefinition.message_templates`.
- `dependencies.get_message_template_factory()` builds the factory from the new
  `MonitorSettings.contact` dict; `get_monitor_loader()` and `get_notifier()`
  both use it.  The notifier holds the settings level set, which is what batch
  subjects render from.

### Notifier

- Every message - alert, report, info, notify, error, and `test-notify` - is
  now rendered from a template.  The hand written `_alert_body` /
  `_report_message` / `_info_body` / `_error_body` builders are gone; their
  wording became the built in defaults.
- Rendering happens **per contact**, so `contact` / `contact_channel` are
  accurate.  Email contacts that received an identical message still share one
  email, so a contact list produces one mail with several recipients.
- Combined notifications: each monitor's fragment is rendered **eagerly in
  `notify()`** (one per alert) and held in `_Pending` as a rendered string.
  `flush()` joins the fragments (`\n\n` for text, concatenation for html),
  applies the channel cap, and uses the rendered `batch_subject`, falling back
  to the first fragment's subject when it renders empty.
- A template that fails to render logs an error and drops **that one message**;
  the run and the other contacts continue.  A template that renders empty sends
  nothing.
- `test-notify` renders the real template for the requested contact type and
  channel against a placeholder `MonitorResult` (sample alert, report, test
  result), prefixing the subject with `test:`.

### Configuration and docs
